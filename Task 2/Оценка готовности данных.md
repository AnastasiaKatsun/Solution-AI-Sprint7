## **ADR флагманской инициативы #1**

### **ADR-001: Выявление подозрительных операций — данные, размещение, модель**

**Дата:** 2026-09 \| **Статус:** Принято

#### **Контекст**

Банк теряет на мошенничестве, схемных операциях и невозвратах. Пороговые правила и внешние сигналы помечают \~35K операций/мес, служба финмониторинга (25 человек) разбирает \~10K — очередь растёт. За прошлый год — два предписания надзора. \~600 приостановок в мес, из них \~450 снимаются (ложные блокировки), 120 клиентов пишут жалобу, часть уходит.

Данные: 20–25 млн операций/мес (сумма, назначение, контрагент, ОКВЭД, дата, канал), история за несколько лет. Прямой метки «схема / не схема» нет. Три следа: «эскалировано» (\~400/мес), исход расследования, подтверждённые случаи (единицы, с задержкой месяцев). Все следы смещены: операции отбирались правилами, не случайно.

#### **Жёсткие ограничения**

1. **Банковская тайна** (ФЗ «О банках и банкинг. деятельности», ст. 26): данные об операциях и счетах не покидают контролируемый периметр банка без договора с обработчиком и комплаенс-разрешения.
2. **Персональные данные** (152-ФЗ): назначение платежа может содержать ПД; среди клиентов — ИП, среди связанных лиц — поручители-физлица. Решения solely на автоматизированной обработке, затрагивающие права субъекта, — допустимы лишь при установленных законом условиях, субъект вправе возразить.
3. **Регуляторика ПОД/ФТ:** решение встраивается в правила внутреннего контроля, не отменяет установленной процедуры. Модель не выносит вердикт — человек в цикле.
4. **Объём и скорость:** 20–25 млн операций/мес, near-real-time (продакшен), батч (пилот).

#### **Решение по данным**

**Путь:** постановка без учителя — сервис приоритизации ручной проверки.

**Обоснование.** Подтверждённых схем — единицы. Обучение с учителем на этом объёме невозможно. Слабые метки (эскалация) воспроизводят логику существующих правил из-за смещения отбора. Сервис приоритизации не выносит вердикт «схема / не схема», а меняет порядок очереди аналитиков.

**Программа сбора разметки (параллельно с пилотом):**

* **Вероятностная контрольная выборка:** 500 операций/мес, случайная, стратифицированная по сегментам (сумма: \<100K, 100K–500K, \>500K; тип: юрлицо / ИП). Размечается аналитиками по гайдлайну. Стоимость \~1,1 млн ₽/год.
* **Приоритетная очередь:** аналитики размечают операции, выведенные моделью в топ.
* **Двойная разметка:** 100 операций/мес — два аналитика, Cohen's kappa ≥ 0,6.
* **Цель:** через 12 мес — ≥ 5000 размеченных операций (несмещённых) → переход к supervised-классификатору.

**Сроки и стоимость:** пилот — 3 мес (unsupervised). Программа разметки — 12 мес, 1,1 млн ₽/год. Переход к supervised — мес. 12–15.

**Вопросы к комплаенс/DPO (не решаются архитектором):**

1. Допустимо ли использовать текст назначения платежа для feature engineering внутри контура?
2. Нужно ли маскировать текст перед сохранением в feature store?
3. Где физически хранить обученные модели и эмбеддинги назначений?
4. Применимы ли ограничения 152-ФЗ ст. 16 (решения solely на автоматизированной обработке) к сервису приоритизации, если модель не принимает решение о блокировке?

#### **Решение по размещению**

|  | **Пилот** | **Продакшен** |
| --- | --- | --- |
| Размещение | On-premise | On-premise |
| Инфраструктура | Python + scikit-learn + PostgreSQL + Redis | Kafka + ClickHouse + Feast/Redis + Triton |
| Режим | Батч, раз в час | Потоковый, \< 3 сек latency |
| GPU | Не нужен (CPU-only) | Опционально (для графовых эмбеддингов, Phase 2) |

**Обоснование.** Банковская тайна → on-prem. Публичный API и выделенный контур провайдера отсечены. Self-hosting в облаке теоретически допустим, но для пилота удлиняет срок запуска (согласование договора, аудит). On-prem — безопасный выбор, использует существующую инфраструктуру банка.

**План выхода от вендора:** не применим (open-source стек: scikit-learn, CatBoost, Kafka, ClickHouse, Redis, Feast, Triton). Вендорская зависимость отсутствует. При переходе на коммерческую графовую СУД (Neo4j) — план выхода: экспорт графа в CSV, миграция на NetworkX/Spark GraphX.

#### **Решение по модели**

**Двухуровневая архитектура:**

**Уровень 1 — Детектор аномалий (unsupervised).**

* Isolation Forest на табличных признаках (сумма, частота, ОКВЭД-мэтчинг, временные окна, отклонение от исторического поведения счёта).
* Графовые метрики (degree, PageRank, betweenness) на графе контрагентов — пересчёт раз в сутки (batch), кэш в feature store.
* Цель: выявить нетипичные операции, не помеченные правилами → расширение охвата.
* Обучается на всём потоке, без меток → не наследует смещение правил.

**Уровень 2 — Ранжировщик (weak supervision, после накопления).**

* CatBoost на признаках операции + граф-эмбеддингах + текстовых признаках (TF-IDF назначений).
* Прокси-метка: «эскалировано» (с оговоркой: воспроизводит логику правил, не является меткой «схема»).
* Ранжирует операции, отобранные правилами + аномалиями, по приоритету.
* Запускается после Phase 1, когда накоплено достаточно эскалаций для обучения.

**Альтернативы, рассмотренные и отсечённые:**

* GNN (Graph Neural Networks): мощнее, но требует GPU и больше данных; отложено на Phase 2.
* One-class SVM: медленнее Isolation Forest на 25 млн операций, без преимущества.
* Autoencoder: требует GPU, не оправдан без меток.
* CatBoost с самого старта (без unsupervised): обучается на смещённых эскалациях → воспроизводит правила → нет нового охвата.

**Допущения:**

1. Isolation Forest + графовые метрики дают Lift@K ≥ 1,5 vs случайного отбора. (Проверяется в Phase 0.)
2. Текст назначения платежа содержит дискриминативные признаки (TF-IDF добавляет ≥ 5% к Lift). (Проверяется в Phase 0.)
3. Граф контрагентов можно построить из истории операций (достаточно рёбер «клиент → контрагент»). (Проверяется в Phase 0.)
4. Комплаенс разрешит использование текста назначения внутри контура. (Ожидается, но не гарантировано.)

**Риски:**

1. **Качество прокси-меток** — главный. Если Lift@K \< 1,3 после Phase 1 → пересмотр: active learning, экспертная разметка, смена прокси.
2. **Смещение выборки** — решается unsupervised уровнем + вероятностной контрольной выборкой.
3. **Дрейф** — паттерны схем меняются. Триггер: KS-test на распределении входных признаков p \< 0,05 → ретрейн.
4. **Комплаенс-отказ** в использовании текста назначения → fallback на агрегированные текстовые признаки (длина, наличие ключевых слов, шаблонность) без хранения эмбеддингов.
5. **Отток аналитиков** на разметку контрольной выборки → уменьшение пропускной способности очереди. Mitigation: разметка 500 оп/мес = \~100 ч/мес, распределить между 5 аналитиками по 20 ч/мес.

**Триггеры пересмотра:**

* Lift@K \< 1,2 после Phase 1 → пересмотр признакового пространства или переход к графовым методам.
* Накоплено ≥ 5000 размеченных операций и supervised CatBoost даёт Recall ≥ 0,8 → переход к классификатору.
* Графовые признаки не добавляют ≥ 5% к Lift → drop графа, упростить архитектуру.
* Комплаенс запрещает использование текста назначения → fallback на агрегированные признаки.
* Дрейф \> 15% по KS-test → внеочередной ретрейн.

## **Паспорт инициативы — разделы 2–5**

### **Инициатива #1 — Выявление подозрительных операций**

#### **Раздел 2. Качество**

| **Метрика** | **Цель** | **Пояснение** |
| --- | --- | --- |
| Overlap top-1% с эскалациями | ≥ 3× от случайного (1%) | Модель в топ-1% содержит ≥ 3% всех эскалаций — лучше случайного |
| Lift@K (K = 10000) | ≥ 1,5 | Модель в топ-K находит в 1,5× больше эскалаций, чем случайный отбор. Минимум для обоснования vs правил |
| Recall@K (по эскалациям) | ≥ 0,95 от текущего уровня правил | Не хуже правил по полноте в верхней части очереди |
| Precision@K | ≥ 0,15 | Базовая \~0,11 (400 эскалаций / 3500 разобранных). 0,15 — целевой прирост |
| FPR на нормальных операциях (S4–S6) | ≤ 0,02 | Не более 2% ложных алертов на чистых — иначе перегрузка |
| Latency p99 (пилот) | \< 60 сек | Батч-режим |
| Latency p99 (продакшен) | \< 3 сек | Near-real-time |

**Риск качества:** смещение выборки — модель обучается на операциях, отобранных правилами, а должна оценивать все. Решение: двухуровневая схема (unsupervised на всём потоке + weak supervision на отобранных) + вероятностная контрольная выборка.

#### **Раздел 3. Данные**

| Журнал операций (АБС) | 20–25 млн/мес | Структурированные записи | Kafka-топик / батч-выгрузка | ИТ |
| Назначение платежа | 1 строка на операцию | Свободный текст | Часть записи операции | ИТ |

| Подтверждённые схемы | единицы/мес | Структурированные | БД финмониторинга, задержка месяцев | Финмониторинг |

**Прокси-метки (weak supervision):**

* Уровень 1: «эскалировано» — \~400/мес, зашумлён, воспроизводит правила.
* Уровень 2: «исход расследования» — менее зашумлён, задержка.
* Уровень 3: «подтверждённая схема» — эталон, единицы, задержка месяцев.

**Смещение отбора:** все три следа сформированы правилами. Обучение на них воспроизводит правила, не паттерны схем. Решение: unsupervised уровень на всём потоке + контрольная выборка.

**Программа сбора разметки:**

* Вероятностная контрольная выборка: 500 оп/мес, стратифицированная (сумма × тип), разметка по гайдлайну, двойная разметка 100 оп (kappa ≥ 0,6).
* Приоритетная очередь: разметка разобранных моделью топ-операций.
* Цель: 5000 оп за 12 мес → переход к supervised.

**Персональные данные и банковская тайна:**

* Назначение платежа — потенциально ПД.
* Сумма, контрагент, ОКВЭД — банковская тайна.

  2. Нужно ли маскировать текст перед сохранением в feature store?
  3. Где хранить эмбеддинги назначений?

#### **Раздел 4. Эксперимент**

**Phase 0 — Базовый unsupervised (1 мес):**

* Сбор истории за 12 мес. Базовые признаки: сумма, частота, ОКВЭД-мэтчинг, временные окна, отклонение от поведения счёта (скользящее среднее).
* Граф контрагентов: degree, PageRank, betweenness — пересчёт раз в сутки.
* Isolation Forest на всём потоке → top-1% аномалий.
* Метрика: overlap top-1% с историческими эскалациями ≥ 3× от случайного.
* Критерий перехода: overlap ≥ 3× → Phase 1; \< 3× → пересмотр признаков.

**Phase 1 — Ранжировщик на слабом надзоре (2 мес):**

* CatBoost на признаках + TF-IDF назначений + граф-эмбеддинги. Прокси-метка: «эскалировано».
* Train/test split по времени (последние 3 мес — test).
* Метрика: Lift@K ≥ 1,5 vs случайного и vs правил.
* Критерий: Lift@K ≥ 1,5 → Phase 2; 1,2–1,5 → доработка признаков; \< 1,2 → пересмотр подхода.

**Phase 2 — Shadow-режим (2 мес):**

* Модель приоритизирует все 25 млн операций/мес параллельно с правилами. Аналитики не видят скор.
* Сбор статистики: что бы модель пометила vs что разобрали.
* Метрика: эскалации из расширения охвата (операции вне правил, score \> threshold) — сколько оказалось в эскалациях.
* Параллельно: запуск программы разметки (контрольная выборка + приоритетная очередь).

**Phase 3 — Пилот (3 мес):**

* Модель приоритизирует очередь для 5 аналитиков из 25. A/B: 5 с ML vs 5 с правилами.
* Метрики: Lift@K, время на разбор, количество эскалаций, доля ложных приостановок.
* Критерий успеха: Lift@K ≥ 1,5, время на разбор ↓ ≥ 20%, ложные приостановки ↓ ≥ 10%.
* Критерий провала: Lift@K \< 1,2 → откат к правилам, пересмотр.

**Phase 4 — Масштабирование (после пилота):**

* Расширение на все 25 аналитиков.
* Переход на потоковый режим (Kafka + Triton).
* Накопление разметки → переход к supervised (мес. 12–15).

#### **Раздел 5. Развёртывание и надёжность**

**Пилот:** on-premise, батч-режим (раз в час), Python + scikit-learn + PostgreSQL + Redis. Без GPU.

**Продакшен:** on-premise, Kafka (поток), ClickHouse (история + батч-фичи), Feast/Redis (feature store), Triton (serving). Потоковый режим, \< 3 сек latency.

**Fallback:** при падении ML-сервиса — деградация к правилам (пороговые), без потери функционала. Аналитики продолжают разбор по правилам.

**Мониторинг:**

* Дрейф входных распределений: KS-test на ключевых признаках, p \< 0,05 → алерт.
* Дрейф score-распределения: сравнение с baseline, отклонение \> 15% → алерт.
* Latency p99 \> 5 сек → алерт.
* Количество аномалий в час: резкий скачок (\> 3σ) → алерт (возможно, изменение в потоке данных).

**Безопасность:**

* Модели и feature store — только в контуре банка.
* Текст назначений не покидает контур; эмбеддинги хранятся, не экспортируются.
* Аудит-трейл: кто, когда, какой score видел.

### **Инициатива #2 — Оцифровка сканов документов**

#### **Раздел 2. Качество**

| **Метрика** | **Цель** | **Пояснение** |
| --- | --- | --- |
| CER (Character Error Rate) на чистых сканах | ≤ 5% | Публикации PaddleOCR: 2–5% на качественных сканах |
| CER на фото с телефона | ≤ 15% | Бизнес-требование: текст читаем для NER |
| Accuracy классификации типа документа | ≥ 0,90 | 10–12 типов, baseline random 10%. 90% — для автоприменения NER-правил |
| F1 NER (top-15 полей) | ≥ 0,85 | Публикации LayoutLMv3: \~0,90 на FUNSD. 0,85 — запас на русские формы |
| Время пакета (10–20 док.) | ≤ 5 мин | Против 1,5 ч вручную |
| Доля пакетов без ошибок ключевых полей | ≥ 70% | 70% — автопроход, 30% — доразбор оператором |
| Доля пакетов с критическими ошибками | ≤ 5% | Критическая — пропущенное ключевое поле (ИНН, сумма, дата) |

**Риск качества:** фотографии с телефона (плохой свет, перекос, неполный кадр). Mitigation: аугментация при обучении (random rotation, brightness, contrast, crop).

#### **Раздел 3. Данные**

| **Источник** | **Объём** | **Формат** | **Доступ** | **Владелец** |

| Данные из АБС (серебряная разметка) | История ввода | Структурированные | АБС | ИТ |

**Разметка:** создаётся с нуля. Гайдлайн: 10–12 типов (выписка, баланс, ОФР, справка о доходах, договор, паспорт, учредительный документ и т.д.), 15 ключевых полей на тип. 2 разметчика × 2 мес. Двойная разметка 500 документов, Cohen's kappa ≥ 0,7. Стоимость \~1,5 млн руб.

**Смещение отбора:** архив отражает клиентов, подавших на кредит. Новые форматы бухгалтерской отчётности (изменения в формах) могут не быть представлены. Mitigation: периодическое дообучение на новых форматах.

**Репрезентативность:** достаточна для типовых форм; недостаточна для нестандартных (региональные справки, кастомные шаблоны). Mitigation: в гайдлайне — родовые типы («справка о доходах» как суперкласс с подтипами).

**Персональные данные:** сканы паспортов — 152-ФЗ. Кредитные заявки — банковская тайна. Вопросы к комплаенс/DPO:

1. Допустимо ли использовать внешнее OCR-API (Yandex Vision, ABBYY Cloud)? — Если нет, on-prem only.
2. Где хранить распознанный текст и каков срок хранения?
3. Допустимо ли хранить сканы после оцифровки, или нужно удалять?

#### **Раздел 4. Эксперимент**

**Phase 0 — Базовый OCR (1 мес):**

* PaddleOCR на 1000 сканов (500 чистых, 500 фото).
* Метрика: CER ≤ 5% на чистых, ≤ 15% на фото.
* Критерий: CER ≤ 10% на чистых → Phase 1; \> 10% → переход к ABBYY on-prem.

**Phase 1 — Классификация + NER (2 мес):**

* Разметка 5000 документов. ResNet/ViT — классификация типа. LayoutLMv3 — NER.
* Train/val/test 70/15/15.
* Метрики: accuracy ≥ 0,90 (классификация), F1 ≥ 0,85 (NER).
* Критерий: F1 ≥ 0,75 → Phase 2; \< 0,75 → увеличить разметку до 10000.

**Phase 2 — Pilot (2 мес):**

* Пайплайн на 50 реальных заявках параллельно с андеррайтером.
* Сравнение извлечённых полей с ручным вводом.
* Метрики: доля пакетов без ошибок ≥ 70%, критические ошибки ≤ 5%.
* Критерий: доля без ошибок ≥ 60% → Phase 3; \< 60% → доработка.

**Phase 3 — Внедрение (3 мес):**

* Интеграция с клиентским порталом (загрузка) и АБС (выгрузка).
* UI ревью: оператор видит извлечённые поля, правит, подтверждает.
* Обратная связь: исправленные поля → в дообучение.

#### **Раздел 5. Развёртывание и надёжность**

**Пилот:** on-premise, CPU-only (PaddleOCR + Tesseract + ruBERT-NER). S3 для сканов, PostgreSQL для результатов.

**Продакшен:** on-premise, GPU (A10) для ViT/LayoutLMv3. Параллельные воркеры (4–8). Опц. ABBYY on-prem для фото-класса.

**Fallback:** при падении ML-пайплайна — ручной ввод (текущий процесс). При падении OCR-движка — fallback на Tesseract (если PaddleOCR) или наоборот.

**Мониторинг:**

* CER на потоке: выборочная проверка 100 док/мес.
* Доля пакетов с критическими ошибками: \> 10% → алерт.
* Время обработки: p99 \> 10 мин → алерт.
* Появление нового типа документа (classification confidence \< 0,5) → алерт, добавление в разметку.

### **Инициатива #10 — Выявление поддельных документов**

#### **Раздел 2. Качество**

| **Метрика** | **Цель** | **Пояснение** |
| --- | --- | --- |
| Precision@top-5% | ≥ 0,50 | Если 200 подделок в \~100K док/год, random top-5% = 0,01. 0,50 — в 50× лучше |
| Recall на подтверждённых подделках | ≥ 0,60 | Поймать большинство известных — бизнес-требование |
| FPR на чистых (S5–S7) | ≤ 0,03 | Больше 3% ложных → перегрузка СБ |
| Latency на документ | \< 30 сек | Батч-режим |

**Риск качества:** мало реальных позитивов (\~200). Синтетика покрывает известные типы, но не все. Adversarial-природа: злоумышленники адаптируются. Mitigation: периодическое дообучение на новых типах подделок от СБ (раз в квартал).

#### **Раздел 3. Данные**

| **Источник** | **Объём** | **Формат** | **Доступ** | **Владелец** |
| --- | --- | --- | --- | --- |
| Сканы документов (через #2) | \~500/мес | Изображения + текст + метаданные | S3 банка | Кредитный депт. |
| Подтверждённые подделки | \~200 (оценочно) | Разметка СБ | БД СБ | СБ |
| Синтетические подделки | 5000+ | Программно сгенерированные | Создаются | ML-команда |
| Внешние реестры (ФНС, Росстат) | По запросу | API | REST, через шлюз банка | ИТ/комплаенс |
| Метаданные PDF | Часть документов | EXIF, PDF metadata | Из файлов | ИТ |

**Разметка:**

* Реальные: 200 подделок от СБ (с описанием типа подделки) + 800 чистых. Гайдлайн типов: цифровое редактирование, физическое вмешательство, метаданные, подделка печати/подписи. 1 мес работы эксперта СБ.
* Синтетические: программная аугментация чистых документов — вставка цифр, замазывание, склейка, изменение метаданных, удаление элементов. 5000+ примеров. 2 недели ML-инженера.
* Cohen's kappa на реальных (двойная разметка 100 док, 2 эксперта СБ) ≥ 0,6.

**Смещение отбора:** подтверждённые подделки — из дел, дошедших до формального подтверждения. Большинство подделок не подтверждены формально (заёмщик отказался, кредит не выдан). Mitigation: синтетика расширяет покрытие; cross-doc consistency — детерминированный сигнал, не зависящий от разметки.

**Репрезентативность:** низкая по реальным данным. Синтетика покрывает программные методы, но не все ручные (качество печати, бумага). Mitigation: постепенное накопление реальных примеров.

**Персональные данные и банковская тайна:**

* Изображения документов — ПД + банковская тайна.
* API ФНС/Росстат — через существующий защищённый шлюз банка.

#### **Раздел 4. Эксперимент**

**Phase 0 — Forensics baseline (1 мес):**

* ELA + анализ метаданных на 200 реальных подделках + 2000 чистых.
* Бейзлайн: правила (ELA threshold, metadata mismatch) → Precision/Recall.
* Метрика: Precision@top-5% ≥ 0,30 (бейзлайн rules-only).
* Критерий: Precision ≥ 0,30 → Phase 1; \< 0,20 → пересмотр правил.

**Phase 1 — CNN forensics (2 мес):**

* ResNet-50, fine-tuned на 5000 синтетических + 200 реальных.
* Autoencoder для anomaly detection на визуальных признаках.
* Метрика: Recall на подтверждённых ≥ 0,50, Precision@top-5% ≥ 0,40.
* Критерий: Recall ≥ 0,50 → Phase 2; \< 0,30 → больше синтетики, GAN-аугментация.

**Phase 2 — Cross-document consistency (1 мес):**

* Правила: сумма в справке = сумма в выписке; ОКВЭД в документе = ОКВЭД в ФНС; наличие подписи/печати.
* CatBoost на консолидированных признаках (ELA + metadata + CNN + cross-doc).
* Метрика: Precision@top-5% ≥ 0,50, FPR ≤ 0,03.
* Критерий: Precision ≥ 0,50 → Phase 3; 0,30–0,50 → доработка; \< 0,30 → только rules.

**Phase 3 — Pilot (2 мес):**

* Shadow-режим на 100 реальных заявках.
* Сравнение с решением СБ (есть ли подделка).
* Метрика: Precision@top-5% ≥ 0,40, FPR ≤ 0,05.
* Критерий: Precision ≥ 0,40 → внедрение; \< 0,30 → откат к rules-only.

#### **Раздел 5. Развёртывание и надёжность**

**Пилот:** on-premise, CPU (ELA + ExifTool + ResNet). Батч-режим, обработка после пайплайна #2.

**Продакшен:** on-premise, GPU (A10) для CNN. Интеграция с API ФНС через шлюз. Батч-режим.

**Fallback:** при падении CNN — остаются rules (ELA + metadata + cross-doc), без потери базового функционала. При недоступности API ФНС — cross-doc consistency без внешней проверки.

**Мониторинг:**

* Precision@top-5% на потоке: выборочная проверка СБ 50 док/мес.
* FPR: доля ложных алертов \> 5% → алерт, пересмотр threshold.
* Появление нового типа подделки (от СБ) → добавление в синтетический генератор, retrain.
* drift визуальных признаков: распределение CNN-эмбеддингов, отклонение \> 15% → алерт.
