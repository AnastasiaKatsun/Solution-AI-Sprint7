## **Режим обработки**

| **Параметр** | **Пилот** | **Продакшен** |
| --- | --- | --- |
| Режим | **Асинхронный батч** — раз в час | **Потоковый** (near-real-time) |
| Триггер обработки | Cron, каждый час | Kafka event, при поступлении операции |
| Задержка | До 60 минут от операции до score в очереди | \< 3 секунды |
| Повторы | При недоступности Feature Store — retry × 3, затем skip с флагом data_stale | При недоступности — Fallback Manager переключает на правила |
| Работа человека | Аналитик видит приоритизированную очередь в UI, обновляется раз в час | Аналитик видит обновления в real-time, P1 — push-уведомление |

**Обоснование.** На пилоте батч-режим упрощает инфраструктуру: не нужен Kafka-консьюмер в реальном времени, достаточно часовой выгрузки из АБС. Это сокращает срок запуска на 2–3 месяца. В продакшене — потоковый режим, потому что операции нужно приоритизировать до того, как они попадут в ручную очередь (иначе приоритизация запаздывает).

## **Выходной контракт**

**Обязательные поля:** operation_id, timestamp, combined_score, priority_level, model_version.anomaly_detector, data_quality, source_ref.

**Поведение при отсутствии данных:**

* Признак отсутствует → features_missing заполнен, признак заменён на медиану обучения, combined_score помечен флагом imputed.
* Знай клиента недоступен → zkk_signal_disagreement: null, скоринг продолжается без этого признака, fallback_path: null (не считается критическим fallback).
* CatBoost недоступен → rank_score: null, combined_score = anomaly_score, fallback_path: "anomaly_only".
* > 30% признаков отсутствуют → fallback_triggered: true, fallback_path: "rules_only", combined_score не вычисляется, priority_level определяется только по правилам.

**Валидация до бизнес-действия:** combined_score и priority_level проходят через Rule Checker перед попаданием в очередь. Rule Checker может повысить приоритет (правило сработало + score высокий) или понизить (правило не сработало, score умеренный, но STOP-лист чистый). Итоговый priority_level — результат совместного применения, а не чистый выход модели.

## **Уровень автоматизации**

| **Решение** | **Кто принимает** | **Обоснование** |
| --- | --- | --- |
| Приоритет операции в очереди | Модель рекомендует, Alert Router детерминированно мапит на уровень | Модель не может блокировать операцию — только менять порядок разбора |
| Разбор операции | Аналитик (человек) | Регуляторное требование: решение по операции — за человеком, по правилам внутреннего контроля |
| Эскалация на расследование | Аналитик | Только человек может принять решение об эскалации |
| Блокировка операции | Аналитик + комплаенс | Модель не участвует. Решение — по действующей процедуре |
| Помечание «чисто» | Аналитик | Человек |
| Ретрейн модели | ML-инженер (по триггеру) | Автоматический ретрейн недопустим без валидации |

**Цена ошибок и пороги.** Ложный негатив (схема пропущена) — регуляторный риск, предписания надзора. Ложный позитив (лишняя приостановка) — остановленный платёж честного клиента, риск оттока (120 жалоб/мес, часть уходит). Порог priority_level P1 (\>0,8) установлен консервативно — в P1 попадают операции с высокой аномальностью И положительным правилом. Это снижает false positive на нормальных операциях, которые просто нетипичны (сезонность, разовый крупный платёж).

## **Фолбэк**

| **Триггер (наблюдаемый признак)** | **Действие** | **Почему** |
| --- | --- | --- |
| Модель недоступна (timeout \> 5 сек / HTTP 5xx) | Fallback Manager → rules_only: приоритет определяется только пороговыми правилами и внешними сигналами. Флаг fallback_path: "rules_only" | Базовый функционал не теряется — правила работают независимо |
| Feature Store недоступен | Fallback Manager → rules_only + флаг data_stale | Без признаков модель не может работать; правила не требуют признаков |
| \>30% признаков отсутствуют или устарели (TTL) | Fallback Manager → rules_only + список в features_missing | Модель на неполных данных недостоверна |
| OOD: признак за пределами [p1, p99] обучающего диапазона | Флаг ood_detected: true, операция маршрутируется на старшего аналитика (P1) вне зависимости от score | Модель вне зоны компетенции — решение за человеком |
| Combined_score в зоне воздержания [0.45, 0.55] | priority_level = P2, маршрутизация в общую очередь (не P1, не отсеивание) | Модель не уверена — не повышать приоритет, но и не терять |
| Расхождение с сигналом правила (правило сработало, score \< 0.3) | Rule Checker повышает до P2, флаг zkk_signal_disagreement | Правило — самостоятельный сигнал, модель не отменяет его |
| Резкий скачок количества аномалий (\>3σ за час) | Monitoring → алерт ML-инженеру, автоматический переключение в rules_only до разбора | Возможно, изменение в потоке данных (АБС, баг ingestion) |
| Новый клиент / сегмент без истории | Признак «возраст счёта \< 30 дней» → флаг, score не понижается за новизну | Модель не должна штрафовать за отсутствие истории |

## **План мониторинга**

| **Уровень** | **Метрика** | **Порог** | **Действие** |
| --- | --- | --- | --- |
| **Вход** | Доля операций с \>30% отсутствующих признаков | \> 5% → жёлтый алерт | Проверка Feature Pipeline, data quality |
| **Вход** | KS-test на распределении ключевых признаков (сумма, частота) vs baseline | p \< 0,05 → жёлтый алерт | Проверка дрейфа, возможный ретрейн |
| **Вход** | Резкий скачок объёма операций (×3 за час) | \> 3σ → красный алерт | Проверка АБС, возможно переключение в rules_only |
| **Модель** | Дрейф score-распределения (KS-test vs baseline) | p \< 0,01 → красный алерт | Ретрейн по триггеру |
| **Модель** | Доля fallback_triggered | \> 10% за сутки → жёлтый алерт | Проверка доступности моделей и Feature Store |
| **Модель** | Доля ood_detected | \> 5% → жёлтый алерт | Расширение обучающего диапазона или ретрейн |
| **Модель** | Latency p99 (продакшен) | \> 5 сек → красный алерт | Масштабирование, проверка Feature Store |
| **Очередь** | Длина очереди P1 | \> 500 → жёлтый алерт | Перераспределение аналитиков |
| **Очередь** | Время от скоринга до разбора (P1) | \> 4 часа → жёлтый алерт | Недостаточная пропускная способность |
| **Очередь** | Доля операций, разобранных за смену | \< 80% от плана → жёлтый алерт | Пересмотр нагрузки |
| **Бизнес** | Lift@K (K = 10000) vs случайного | \< 1,3 → красный алерт | Ретрейн, пересмотр признаков |
| **Бизнес** | Доля эскалаций в разобранных | \< 8% (база \~11%) → жёлтый алерт | Модель приоритизирует плохо, возможен дрейф паттернов |
| **Бизнес** | Доля ложных приостановок | \> 600/мес → жёлтый алерт | Порог P1 слишком низкий, пересмотр threshold |
| **Бизнес** | Доля размеченной контрольной выборки | \< 80% плана → жёлтый алерт | Накопление разметки отстаёт |

**Что запускает откат:** два последовательных красных алерта по бизнес-метрикам (Lift@K \< 1,3 или скачок ложных приостановок \> 800/мес) → автоматический переход в rules_only, ручной разбор причины, ретрейн с валидацией перед возвратом.

## **Инициатива #2 — Оцифровка сканов документов: описание контейнеров**

### **Режим обработки**

**Синхронно-асинхронный гибрид.** Загрузка документа — синхронная (клиент видит прогресс). Обработка — асинхронная: файл попадает в S3, запускается пайплайн, результат — через 30–60 сек на скан, 1–5 мин на пакет. Аналитик получает уведомление. Время измеряется минутами, не секундами — нет нужды в real-time.

### **Уровень автоматизации**

| **Решение** | **Кто** | **Почему** |
| --- | --- | --- |
| Классификация типа документа | Модель автоматически | Низкая цена ошибки (ошибка классификации → неправильный NER-шаблон, но оператор видит результат) |
| Распознавание текста (OCR) | Модель автоматически | Зрелая технология, цена ошибки — опечатка, которую оператор правит |
| Извлечение полей (NER) | Модель автоматически, оператор ревьюит | Модель извлекает, человек подтверждает или правит. Если confidence \< 0,7 — поле помечено для обязательной проверки |
| Валидация (контрольные суммы, форматы) | Детерминированные правила | Контрольная сумма ИНН, формат даты — не требует ML |
| Запись в кредитное досье | Оператор подтверждает | Финальный commit в АБС — за человеком, не автоматически |

### **Фолбэк**

| **Триггер** | **Действие** |
| --- | --- |
| OCR CER \> 15% на конкретном документе | Документ помечен `low_confidence_ocr` → оператор вводит вручную |
| Doc Classifier confidence \< 0,6 | Документ помечен `unknown_type` → оператор выбирает тип вручную |
| NER не извлёк ключевое поле (ИНН, сумма) | Флаг `critical_field_missing` → обязательный ручной ввод |
| Падение OCR-движка | Fallback на Tesseract (запасной движок); если оба недоступны — ручной ввод |
| Формат не из обученной выборки | Документ обрабатывается generic-NER (ruBERT без LayoutLM), флаг `generic_ner` |

### **Угрозы на границах доверия**

| **Граница** | **Угроза** | **Что делаем** |
| --- | --- | --- |
| **TB1: Клиентский портал → Uploader** | Недоверенный контент: вредоносный PDF (embedded JS, эксплойт), файл подменён | Антивирусное сканирование до попадания в S3; sandbox-обработка (OCR в изолированном контейнере без сети); ограничение размера (50 МБ); только PDF/JPEG/PNG/XLSX |
| **TB1: Клиентский портал → Uploader** | Prompt injection через текст документа (если используется LLM для NER) | NER — LayoutLM/BERT, не generative LLM; текст не интерпретируется как команда; выход модели — структурированные поля, валидируемые правилами |
| **TB2: Uploader → Preprocessor** | Утечка сканов с ПД (паспорта) из S3 | Шифрование at-rest; доступ только Service Account Preprocessor; TTL сканов — согласно политике хранения (вопрос к комплаенсу); аудит доступа |
| **TB3: OCR → NER** | Утечка распознанного текста с ПД | Текст не покидает контур; NER работает on-premise; результаты в PostgreSQL с шифрованием; доступ по RBAC |
| **TB4: Review Queue → Оператор** | Несанкционированный доступ к чужому кредитному досье | RBAC: оператор видит только назначенные ему заявки; аудит; watermarking на экране (ID оператора) |

## **Инициатива #10 — Выявление поддельных документов: описание контейнеров**

### **Режим обработки**

**Пакетный (батч).** Обработка запускается после завершения пайплайна #2 (оцифровка). Каждый документ — 10–30 сек на CPU, 3–5 сек на GPU. Не real-time: решение по кредиту занимает дни, десятки секунд на проверку подлинности не критичны.

### **Уровень автоматизации**

| **Решение** | **Кто** | **Почему** |
| --- | --- | --- |
| Forensics (ELA, metadata, CNN) | Модель автоматически | Выставляет risk-score, не блокирует |
| Cross-document consistency | Детерминированные правила | Сумма в справке = сумме в выписке — не требует ML |
| External verification (ФНС) | Автоматический запрос через шлюз | Сверка с реестром — детерминированная |
| Risk scoring (CatBoost ensemble) | Модель автоматически | Объединяет все сигналы в финальный скор |
| Эскалация в СБ | Модель рекомендует (score \> порог), человек подтверждает | СБ решает, является ли это подделкой; модель только помечает |
| Отказ в кредите | Андеррайтер / кредитный комитет | Модель не отказывает — только сигнализирует риск |

### **Фолбэк**

| **Триггер** | **Действие** |
| --- | --- |
| CNN-модель недоступна | Остаются rules (ELA + metadata + cross-doc), флаг `cnn_unavailable`, скор на основе детерминированных сигналов |
| API ФНС недоступен | Cross-doc consistency без внешней верификации, флаг `external_verifier_unavailable`; документ не получает penalty за непроверку с ФНС |
| Autoencoder OOD (визуальные признаки вне обученного диапазона) | Флаг `visual_ood`, документ маршрутируется на ручную экспертизу СБ |
| Risk score в зоне [0.4, 0.6] | Не эскалируется автоматически, но помечается `review_recommended` для андеррайтера |
| Все сигналы противоречат друг другу (ELA: чисто, cross-doc: несовпадение, metadata: ОК) | Флаг `conflicting_signals`, документ → ручная экспертиза СБ |

### **Угрозы на границах доверия**

| **Граница** | **Угроза** | **Что делаем** |
| --- | --- | --- |
| **TB1: Пайплайн #2 → Signal sources** | Отравление upstream: искажённые поля или изображения из пайплайна #2 | Контрольная сумма полей; сверка с исходным сканом в S3; если поля из #2 противоречат метаданным скана — флаг |
| **TB1: Пайплайн #2 → Signal sources** | Недоверенный контент: вредоносный файл от клиента прошёл через #2 | Изображения обрабатываются в sandbox; CNN не выполняет код из файла; только предсказание |
| **TB2: External Verifier → ФНС** | Перехват запроса к ФНС (MITM); утекает ИНН заёмщика | mTLS через шлюз банка; логирование без тела; rate limiting; кэш ответов 24ч |
| **TB2: External Verifier → ФНС** | ФНС отдаёт некорректные данные | Сверка: данные из ФНС vs данные из документа; расхождение — флаг, не автоматический отказ |
| **TB3: Model Registry → Models** | Подмена весов CNN (adversarial: веса настроены пропускать определённый тип подделок) | Подпись моделей; CI/CD с ревью; только ML-инженер деплоит; версионирование; откат за \< 5 мин |
| **TB4: Alert → СБ** | Утечка сканов и признаков подделки за пределы СБ | RBAC: только СБ видит алерты и PDF-отчёты; сканы не вкладываются в отчёт — только ссылка на S3; аудит доступа |

## **Обоснование состава звеньев**

**Инициатива #1 (табличный скоринг):** состав звеньев — «признаки → модель → калибровка и порог → детерминированные бизнес-правила». Retrieval не нужен: нет внешнего контекста, который нужно подтягивать к операции. Модель — два звена (Isolation Forest для аномалий + CatBoost для ранжирования), оба табличные. Никаких LLM, промптов или инструментов — постановка не требует работы с текстом как с языком, только TF-IDF как признаковое пространство. Человек — в конце цепочки, встроен в существующий процесс финмониторинга, не поставлен рядом.

**Инициатива #2 (документы):** состав звеньев — «получение документа → предобработка → классификация (ML) → OCR (ML) → извлечение полей (NER, ML) → валидация (детерминированная) → ревью (человек)». Retrieval не нужен: нет поиска по базе знаний, документ обрабатывается сам по себе. Промпт и LLM не используются: LayoutLMv3 — модель для NER с layout-aware признаками, не генеративная. Дообучение — при появлении новых форматов документов.

**Инициатива #10 (документы, forensics):** состав звеньев — «метаданные (детерминированные) + визуальные признаки (CNN, ML) + cross-doc consistency (детерминированные) + external verification (API) → ensemble scoring (ML) → эскалация (человек)». Multi-signal: ни одно звено не решает само, ensemble объединяет. LLM не нужен: задача — классификация и anomaly detection, не генерация. Промпт не нужен: нет свободного текста для интерпретации.
